## 本地优化: Ugly/UglyInPlace 只读快进

同步上游时必须保留. 输出与上游逐字节一致, 只改变扫描方式:

- 先只读扫描到字符串外第一个可删除字节 (`<= ' '`), 此前内容原样保留. `UglyInPlace` 遇到无空白输入时不写内存, 直接返回原切片; `Ugly` 始终返回独立副本, 不与输入共用底层数组.
- 之后的压紧和前缀扫描相同: 字符串前 16 字节逐字节处理, 更长的部分用 `IndexByte` 跳到下一个引号再整段复制. 只用 `IndexByte` 时短字符串反而变慢; 按 8 字节并行比较 (SWAR) 的方案在短键值 JSON 上慢约 2 倍, 均已否决.
- 原地压缩时, 已复制的字符串在 src 中可能已被覆盖, 所以长字符串的反斜杠奇偶回溯在 out 上进行, 回溯最远停在开引号.

验证: 与旧逐字节实现 (测试内 `uglyReference`) 30 万组随机差分及边界表一致 (`TestUglyMatchesReferenceRandom`, `TestUglyBoundaryCases`), 原生 fuzz `FuzzUgly` 约 4400 万次无差异, 测试同时检查两种入口的所有权契约. 基准为 `BenchmarkUglyShapes`, 原地版本计时包含每轮恢复输入的复制.

评估过但不采纳: `Ugly` 的 `make` 会先清零整个缓冲区. 改用 `append([]byte(nil), json...)[:l:l]` 可以免清零, 且仍保持 `cap == len`, 但收益只在大输入上出现 (1.5MiB 时清零约 85µs, 不超过 8%), 600B 时测不出差别, 而仓内唯一调用方是 gjson 的 `@ugly` 修饰符, 不在热路径上.

该循环对代码对齐非常敏感, 同一份旧代码平移 32 字节可相差约 35%. 对比时须用多种布局平移 (例如在包内插入填充函数) 并取中位数, 不能只跑单个二进制.

## 已知问题 (上游同样存在, 暂不修改)

- 输出长度随嵌套深度平方增长, 递归过深还会栈溢出. 只用于格式化可信数据.
