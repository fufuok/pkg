# sjson

源自 [tidwall/sjson](https://github.com/tidwall/sjson) v1.2.9, 包路径改为 `github.com/fufuok/pkg/xjson/sjson`, 依赖本仓库的 `xjson/gjson`.

## 对上游的修正

以下修正在同步上游时必须保留, 每项都有回归测试.

| 位置 | 上游问题 | 本地修正 | 回归测试 |
| --- | --- | --- | --- |
| `maxpad` (`appendBuild`/`appendRawPaths`) | 只限制每层补齐. 路径 `a` 后重复 100 次 `.100000` (701 字节) 仍生成约 50MB 合法 JSON, 累计分配约 240MB, 且不报错 | 单次调用中所有层的补齐合计不超过 100000 个 null, 超出返回错误并保留原 JSON. 先判本层再判累计: 任一层单独超限 (包括上层已有补齐时) 仍返回上游原有错误信息, 只有累计超限才报 `total padding`, 下标为 `math.MaxInt` 时错误文本不会溢出成负数 | `TestPadTotalBudget` |
| `setComplexPath` | gjson 返回的偏移并不总指向原文: 管道 `\|` 之后的 `Indexes` 相对的是子值, `#` 之后接 `!` 静态值、修饰符或子选择器时等于父元素偏移, 嵌套 `#` 时也可能错位. 上游直接按偏移切片, 会 panic (如 `Set("[1]", "#.!true", v)`)、拼出非法 JSON (如 `Set("[12,13]", "#(>10)#.!1", "x")` 得 `["x"2,"x"3]`), 或在内容碰巧相同时改写别的字段而输出仍合法 (如对 `{"xy":1,"a":[{"b":1}]}` 写 `a\|#.b` 会改掉 `xy`, `[12,13]` 经 `#(>10)#.!1` 写 9 得到 `[92,93]`, JSON Lines 中 `..#(id==3).t.#.v` 改的是第 1 行). 路径来自外部输入时, 单个请求即可触发 | 多结果只在偏移可信时写入: 路径中没有任何未转义的 `\|` (查询值里的也算, 因为对象上的 `#(` 不是查询); 没有以 `{`、`[`、静态值 `!` (判定同 gjson `execStatic`, `!x` 这类是普通键名)、已注册修饰符 `@name` 开头的路径段 (查询体内同样检查; `@timestamp` 等未注册名是普通键名); 多结果来源 (段首 `#.`、结尾 `#`、`#(...)#`) 至多一个, 嵌套多结果只记录外层元素偏移. 单匹配查询后再取多结果的偏移由 gjson 修正后可正常写入. 每个写入点须内容一致, 且前后是值的分隔符 (排除数字前缀和键名位置), 区间互不重叠. 偏移 0 只对 JSON Lines 路径 (以 `..` 开头) 放行, 单结果还须与原文共享起始内存, 以排除无匹配时计算出的 `[]` 恰好等于整个文档. 先校验全部写入点再修改, 任一不满足即不修改也不报错, 与路径不存在时一致. 语义模型差分 (3 个种子, 各约 21.6 万条复杂路径): 错写 0、非法输出 0, 上游错写约 3900 次、panic 约 40 次; 相对上游写对的情形约 2.3% 被保守拒绝, 均为 `#` 后接恒等修饰符 (`#.@this`) 或查询值含 `\|` | `TestComplexPathUnlocatable`, `TestComplexPathMisplaced` |
| `atoui` | 超过 8 字节的路径段直接调用 `strconv.ParseUint`, `q_utm_source` 这类普通键名每次生成一个错误对象, `SetBytes` 新增键从 3 次分配变为 5 次 | 先确认全为数字再解析, 普通键名不分配 | `TestAtouiNoAlloc` |
| `deleteTailItem` | 删除以转义引号开头的键 (如 `\"`) 时多退一位, 越过键的起始引号, 误删前一个键或留下 `{"\"":,"y":2}` 这类非法 JSON | 去掉多余的回退 | `TestDeleteKeyLeadingEscapedQuote` |
| `set` 乐观原地替换 | 同时开启 `Optimistic` 和 `ReplaceInPlace` 时, 写入需要转义的字符串 (非 ASCII、引号、控制字符) 会原样返回输入, 修改被静默丢弃 | 需要转义时改走分配新切片的路径 | `TestOptimisticInPlaceEscape` |

## 已知问题 (上游同样存在, 暂不修改)

- `maxpad` 只约束单次调用. 对同一文档用多个外部路径反复 `Set` 时, 每次仍可补齐 100000 个 null (约 500KB), 增长会累积. 例如约 4KB 的查询串含 364 个 `xx.99999` 键时, 正文累计约 173MB, 分配约 70GB. 把外部输入当路径的调用方须自行限制总大小, 或先用转义把外部键当作普通键名.
- 路径键含非法 UTF-8 时, 每次 `Set` 都会追加一个重复键. 写入时键被替换为 U+FFFD, 下次查找按原字节比较而找不到.
- 开启 `Optimistic` 时, 以 `..` 开头的路径按 gjson 的 JSON Lines 语义处理, 可能替换整个文档.
- 路径中间经过的值是内容像 JSON 的字符串时, 会被当作容器写入并破坏结构. 例如对 `{"a":"[1,2]"}` 写 `a.1` 得到 `{"a":"[1,"x"]"}`, 且不报错. 源于 gjson 对字符串结果继续取值的行为, v1.4.2 相同. 外部输入作路径时先转义键名, 或写入后校验.
- `..0` 等不含特殊字符的 JSON Lines 路径按普通键路径处理, 不会定位到对应行.
- 上游 v1.2.6 起的行为变化 (NaN/Inf 报错、补齐上限 100000、空路径表示空键等) 见 [xjson/README.md](../README.md).
